# Фоновые задачи и индексация

## Назначение и запуск

Задача объявлена в `backend/app/celery_config.py`. Её сообщение содержит идентификатор контракта и служебные параметры попытки; они не входят в публичный API.

```text
indexing.load_contract(contract_id)
```

Обработчик запускается командой:

```bash
python -m celery -A app.celery_config worker -l info --concurrency=2
```

Очередь и результаты используют Redis из `CELERY_BROKER_URL` и `CELERY_RESULT_BACKEND`. Сериализация — JSON, часовой пояс — UTC. Отдельные очереди и Celery Beat не используются.

## Пропускная способность анализатора

Анализатор принимает до двух одновременных запросов компиляции или Slither. Compose ограничивает обработчик двумя параллельными задачами. При заполнении анализатор возвращает HTTP 503 с `Retry-After: 5`; клиенты повторяют только такой ответ, до 18 повторов и не более 90 секунд суммарного ожидания. Другие ответы 503, в том числе отсутствие компилятора, не повторяются. При нескольких обработчиках учитывайте их суммарное число параллельных задач.

## Жизненный цикл задачи и защита от устаревших попыток

1. API получает блокировку Redis со случайным токеном владельца.
2. В одной транзакции сохраняет состояние `indexing`, UUID попытки, время активности и идентификатор задачи.
3. Публикует сообщение Celery. Ошибка публикации условно завершает текущую попытку как `failed`.
4. Обработчик атомарно захватывает попытку через условный `UPDATE ... WHERE indexing_claimed_at IS NULL`. Дубликат возвращает `skipped` и не освобождает чужую блокировку.
5. Обработчик последовательно выполняет компиляцию, Slither, векторизацию и оценку. Перед каждой записью блокирует строку и проверяет UUID и статус. Между этапами обновляет время активности.
6. Только успешная фиксация `ready` публикует новое `analysis_generation_id`.
7. В `finally` блокировка Redis удаляется лишь при совпадении токена владельца.

Координация API находится в `contract_service._enqueue_indexing`, обработка — в `indexing_worker.run_indexing`, проверки актуальности — в `indexing_lifecycle.py`. Устаревший обработчик не может перезаписать AST, отчёт или состояние новой попытки.

## Поколения Qdrant

Точки содержат UUID попытки в `indexing_attempt_id` и идентификаторе точки. Замена ограничена парой `(contract_id, indexing_attempt_id)`; поиск фильтрует успешное поколение из PostgreSQL. Ключи Redis и `analysis_reports` учитывают то же поколение, поэтому повторный анализ не читает прежние ответы.

Старые завершённые контракты с UUID `NULL` сохраняют совместимость с прежними точками. При сбое после записи в Qdrant поколение остаётся невидимым до состояния `ready`. Сверка сохраняет успешное и выполняющееся поколения, удаляя остальные и точки удалённых контрактов.

## Блокировка и повторные запросы

```text
indexing_lock:{user_id}:{chain_id}:{address}
```

Ключ хранит токен владельца с TTL 3600 секунд. Токен передаётся только задаче Celery, скрывается в `argsrepr` и не возвращается клиенту. Lua атомарно сравнивает значение и удаляет ключ. Старый обработчик после истечения TTL не может удалить блокировку следующего владельца.

Повторный анализ завершённого контракта возвращает существующую запись с `reused=true`. Выполняющаяся индексация или занятая блокировка даёт `409`. После `failed` создаётся новая попытка.

Redis ограничивает допуск, но не гарантирует согласованность БД. API дополнительно проверяет `contracts.status`; уникальный индекс `(user_id, address, chain_id)` препятствует дублированию записей. Строковые блокировки и UUID защищают записи PostgreSQL, а поколения разделяют точки Qdrant.

Общего предельного времени задачи Celery нет: `task_time_limit` и `task_soft_time_limit` не заданы. TTL может истечь раньше завершения задачи; он не является сроком её выполнения. Продление блокировки для выбранного механизма восстановления не требуется, поскольку согласованность обеспечивается проверкой попытки в БД.

## Матрица отказов и восстановление

| Отказ | Состояние | Восстановление |
|---|---|---|
| Брокер недоступен при публикации | Текущая попытка получает `failed`, освобождается только её блокировка | Повторить анализ после восстановления брокера |
| API погиб после фиксации БД, до публикации | Запись остаётся `indexing`, захват отсутствует | Сверка после порога простоя завершает её как `failed`; затем возможен повтор |
| Повторная доставка | Только одна доставка захватывает попытку | Дубликаты возвращают `skipped` |
| Сбой после записи Qdrant, до `ready` | Точки поколения есть, но недоступны чату | Сверка завершает зависшую попытку и удаляет неактивные точки |
| Потеря обработчика | При жёстком завершении может остаться `indexing` | После освобождения соединения строковая блокировка снимается; сверка завершает зависшую попытку |
| Истечение TTL Redis | Состояние БД всё ещё блокирует повтор через `409` | Выполнить сверку после порога простоя и повторить анализ |
| Окончательная ошибка обработки | Текущая попытка получает `failed` и безопасное сообщение | Исправить причину и запустить новую попытку |

Автоматический повтор задач Celery, `acks_late` и `reject_on_worker_lost` не включены: безопасность повторного выполнения всех внешних действий не доказана. Повторы HTTP при перегрузке анализатора выполняются внутри уже захваченной попытки.

## Детерминированная сверка зависших записей

Для одного хоста предусмотрен пользовательский таймер systemd в `deploy/systemd/`. Он запускает `reconcile_indexing` каждые 15 минут, начиная через 5 минут после старта пользовательского диспетчера. Порог простоя — 3600 секунд с последнего сигнала активности; для старых записей без него используется `created_at`.

Замените `%h/chainwise` в файле службы на путь к рабочей копии, если он отличается. Устанавливайте таймер от пользователя с доступом к Docker:

```bash
mkdir -p ~/.config/systemd/user
cp deploy/systemd/chainwise-indexing-reconcile.{service,timer} ~/.config/systemd/user/
# При необходимости поправьте WorkingDirectory в ~/.config/systemd/user/chainwise-indexing-reconcile.service
systemctl --user daemon-reload
systemctl --user enable --now chainwise-indexing-reconcile.timer
systemctl --user list-timers chainwise-indexing-reconcile.timer
```

Для работы без активного входа пользователя включите режим `linger`. Журнал доступен через `journalctl --user -u chainwise-indexing-reconcile.service`. Первый запуск выполните без применения изменений:

```bash
docker compose exec -T backend python -m app.scripts.reconcile_indexing
docker compose exec -T backend python -m app.scripts.reconcile_indexing --apply
docker compose exec -T backend python -m app.scripts.reconcile_indexing --apply --stale-after-seconds 3600
```

Без `--apply` команда только показывает кандидатов. С применением блокирует строки, повторно проверяет статус и завершает зависшие попытки как `failed`, затем очищает Qdrant. Активные и завершённые записи сохраняются. Повторный запуск безопасен; новые задачи не публикуются. При остановленном сервере служба завершится ошибкой и повторится по следующему таймеру.

## Операционная диагностика

```bash
docker compose ps
docker compose logs celery-worker
docker compose logs slither
curl -s http://localhost:8001/api/v1/contracts/CONTRACT_ID/status \
  -H "Authorization: Bearer ACCESS_TOKEN"
```

Проверяйте `status`, `indexing_step`, `last_error`, время активности и доступность зависимостей. `/health` проверяет зависимости API, но не наличие обработчика Celery и не готовность очереди.
